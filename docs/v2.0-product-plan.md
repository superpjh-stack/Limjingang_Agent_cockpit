# 임진강김치 Agent v2.0 재기획

작성일: 2026-09-23 · 상태: 제품 기획안 / 구현 전

## 1. 제품 방향

**모바일에서는 현장에서 말로 확인하고, PC에서는 근거를 검토해 업무를 마무리하는 제조 업무 에이전트.**

성공의 기준은 대화 횟수가 아니라 ‘확인해야 할 일을 찾고, 근거를 이해하고, 다음 담당자에게 정확히 넘겼는가’다. 화면의 중심 단위를 메뉴·질문에서 **업무 건**으로 바꾼다. 업무 건에는 LOT, 질문, 근거, 메모, 담당자, 진행 상태가 함께 연결된다.

현재 프로젝트에는 이미 React V2가 있고 패키지와 API 버전도 2.0.0이다. 이번 문서의 v2.0은 그 코드 기반의 **고객 경험 재설계**를 뜻한다. 별도 V3나 중복 앱을 만들지 않고 기존 `v2/`를 확장한다. 루트 Streamlit V1은 유지한다.

이번 산출물은 기획과 개발 명세다. 아래 신규 기능이 구현·배포되었다는 뜻은 아니다.

### 기획의 전제

- 직접 사용자는 생산 작업자, 품질 담당자, 출하·영업 담당자, 운영 책임자로 가정한다. 실제 역할과 작업 환경은 현장 인터뷰로 검증한다.
- 거래처는 납기·품질 안내를 받는 간접 고객이다. 이번 범위는 직원의 대응 여정까지이며, 거래처용 로그인 포털은 후속 검토한다.
- 공용 단말, 소음, 장갑, 이동, 통신 불안정은 설계 시나리오다. 위생구역 내 개인기기 사용 가능 여부와 실제 장갑 조작 가능성은 현장에서 확인한다.
- 기존 데이터는 2026년 9월 샘플이다. 오늘의 생산현황·실시간 예측으로 표시하지 않는다.
- 조회·정리·검토 업무를 지원한다. 공정 변경, 출하 승인, 발주, 외부 고객 발송은 별도 권한과 확정 행위가 필요한 업무다.

## 2. 현재 제품 진단

README뿐 아니라 `v2/web/src/App.tsx`, `types.ts`, `styles.css`, `v2/api.py`, 공유 저장소와 API 테스트를 확인했다. 이번 진단은 코드 기준이며 실기기 사용성 검증 결과는 아니다.

| 영역 | 현재 확인된 구현 | 사용자가 겪을 문제 | v2.0 방향 |
|---|---|---|---|
| 시작 화면 | KPI·주의 기록·공정 요약 | 무엇부터 끝내야 하는지 사용자가 해석 | 우선 업무와 이어 할 업무를 먼저 표시 |
| 모바일 | PC 콘텐츠 반응형 + 별도 대화 패널 | 현장 질문까지 여러 조작, 화면과 대화가 분리 | 현장 홈·음성 진입·한 건씩 처리 |
| 음성 입력 | 녹음 파일 업로드 후 텍스트 변환 | 기기 녹음·파일 선택을 거쳐야 함 | 브라우저에서 탭으로 녹음 시작·종료 |
| 음성 출력 | 답변 전체 음성 생성·재생 | 긴 답변, 명시적 정지 UI 부재 | 짧은 요약 듣기·정지·재생 상태 |
| 질문 문맥 | LOT 상세의 질문에 LOT 전달 | 후속 질문은 LOT를 다시 적어야 할 수 있음 | 선택한 LOT·업무·기준일을 입력창 위에 유지 |
| 업무 연속성 | React 메모리 대화, 서버 메모리 연결 | 새로고침·PC 전환·서버 재시작 후 업무 복구 어려움 | 사용자별 저장 업무와 기기 간 이어보기 |
| 근거 확인 | 문서 상세, 조회 기록 첫 건 보기 | 여러 기록 비교와 완료 판단이 번거로움 | 모든 근거 탐색·문서와 실측 구분·누락 표시 |
| 인증 | 공통 접근 코드로 유료 호출 보호 | 담당자 식별·역할 구분·인계 불가 | 조직 로그인과 업무별 접근권한 |
| 데이터 신뢰 | 샘플 표시는 있으나 일부 날짜·표현 고정 | 오래된 기록 또는 예측 누락을 오해할 가능성 | 데이터 시각·조회 시각·미확인 구분 |
| 구조 | 업무 화면·대화·음성이 App.tsx에 집중 | 녹음·전송·초기화 간 상태 충돌 관리 어려움 | 업무·문맥·대화·음성 상태를 분리 |

특히 `abnormal_risk ?? 0`로 표시를 결정하는 부분은 예측 부재를 낮은 위험처럼 보이게 할 수 있다. ‘예측 없음’과 ‘샘플 낮은 위험’을 명확히 분리한다. 현재 AI 응답 API의 `records`는 빈 배열로 반환되므로, 문서 외 DB 근거의 연결도 보강해야 한다.

## 3. 사용자별 기대 경험

| 사용자 | 시작 상황 / 하고 싶은 일 | 모바일 역할 | PC 역할 | 완료의 정의 |
|---|---|---|---|---|
| 생산 작업자 | 교대 시작, 해당 LOT 확인 | 짧은 브리핑, LOT 질문, 현장 메모 | 인수인계 확인 | 확인사항과 미해결 항목을 남김 |
| 품질 담당자 | CCP 주의·발효 이상 검토 | 현장에서 기록 확인, 추가 확인 메모 | 계보·실측·기준 문서 비교 | 근거와 검토 결과, 후속 담당자를 기록 |
| 출하·영업 담당자 | 출하 대기, 납기 문의 | 관련 LOT 빠른 조회 | 출하 근거 확인, 회신 초안 작성 | 승인 상태를 확인해 고객 안내 준비 |
| 운영 책임자 | 병목·미처리 업무 파악 | 핵심 현황 듣기 | 미처리·담당자·처리시간 검토 | 책임자와 후속 일정이 정해짐 |

역할 선택은 홈 화면 개인화에만 사용한다. 실제 권한은 서버에서 부여하며, 화면의 역할 선택으로 권한이 바뀌지 않는다.

## 4. 공통 고객 여정

**발견 → 대상 확인 → 질문 → 근거 검토 → 다음 행동 → 저장·인계 → 재방문**

| 단계 | 사용자 마음 / 질문 | 제품이 제공할 경험 | 완료 신호 | 측정 |
|---|---|---|---|---|
| 발견 | “지금 무엇부터?” | 우선 업무 3개, 사유, 데이터 기준시각 | 업무 건 열기 | 첫 업무 진입 시간 |
| 대상 확인 | “이 LOT가 맞나?” | 제품·공정·전체 LOT ID 확인 | 문맥 선택 확정 | 잘못된 LOT 수정률 |
| 질문 | “길게 입력하기 어렵다” | 음성·문자·맥락 추천 질문 | 질문 제출 | 음성 전송 완료율 |
| 근거 검토 | “왜 그런 답이지?” | 결론, 근거, 누락, 다음 확인 | 근거 열람 | 근거 확인율 |
| 다음 행동 | “이제 누구에게 무엇을?” | 다음 확인 버튼과 담당자 연결 | 메모 또는 검토 결과 작성 | 다음 행동 전환율 |
| 저장·인계 | “내가 한 일을 알까?” | 저장 확인, 상태와 담당자, 수신 확인 | 인계 저장 및 수신 확인 | 미확인 인계 건수 |
| 재방문 | “어디까지 했지?” | 저장 업무, 마지막 검토점, 새 근거 표시 | 이어보기 | 업무 복구 성공률 |

일반 질의는 저장 없이 이용할 수 있다. 추적이 필요한 질문에서 ‘업무로 저장’을 선택하거나 우선 업무를 열 때 업무 건을 만든다. 모든 질문을 자동으로 업무로 등록하지 않는다.

### 여정 A. 모바일에서 현장 확인, PC에서 품질 검토

1. 작업자가 현장 홈에서 ‘발효 검토 필요’ 업무를 연다. 날짜와 샘플 여부를 확인한다.
2. LOT를 선택하고 ‘말하기’를 누른다. “이 LOT에서 확인할 게 뭐야?”라고 말한 뒤 종료한다.
3. 변환된 문장과 LOT를 확인한다. 틀린 번호는 후보 목록에서 고친 뒤 전송한다.
4. ‘확인사항 요약 → 근거 → 다음 확인’ 답변을 받는다. 원하면 짧은 요약을 듣는다.
5. 현장 메모를 작성하고 ‘내 업무에 저장’한다. 공유가 필요하면 수신자를 확인해 ‘인계’한다.
6. 품질 담당자가 PC의 인계함에서 같은 업무를 열고 계보·측정·기준 문서를 비교한다.
7. 검토 결과와 미해결 항목을 저장한다. 인계받았다는 확인과 검토 완료를 구분한다.

화면 예시 문구: “선택 LOT의 측정 기록과 연결된 CCP를 확인하세요. 누락된 기록이 있어 현재 자료만으로 출하 가능 여부를 확정할 수 없습니다.” 실제 응답은 조회된 데이터에 따라 생성한다.

### 여정 B. PC에서 출하 검토, 현장에서 추가 확인

1. 출하 담당자가 ‘출하 검토’ 목록에서 승인대기 업무를 연다.
2. 완제품 LOT와 연결 공정의 CCP, 승인 기록, 누락 근거를 한 화면에서 확인한다.
3. ‘추가 확인 요청’으로 담당자·요청사항·기한을 지정해 내부 업무를 인계한다.
4. 현장 담당자가 모바일에서 업무를 열고 메모를 저장한다.
5. PC에서 갱신 내용을 확인하고 회신 초안을 작성한다. 검토 완료가 ERP 출하 승인으로 바뀌지는 않는다.

### 여정 C. 거래처 문의·클레임 대응

1. 직원이 거래처명·출하번호·클레임번호로 기존 기록을 찾는다.
2. 불명확한 번호는 후보를 확인하고 출하 → 포장 → 연결 공정을 추적한다.
3. 에이전트가 확인된 사실, 미확인 사항, 추가 확인 담당자를 구분해 정리한다.
4. 내부 검토용 초안과 고객 회신용 초안을 구분한다. 고객 초안에는 불필요한 내부 메모·원가·타 거래처 정보를 넣지 않는다.
5. 담당자가 초안을 수정하고 확정본을 복사·내려받는다. 초기 버전에는 고객 자동 발송을 넣지 않는다.
6. 기존 채널로 회신한 뒤 회신 일시와 후속 약속을 업무에 기록한다.

신규 클레임 접수와 ERP 등록까지 필요한지는 후속 현장 조사에서 확정한다. 초기 범위는 기존 기록의 조회·검토·대응 초안이다.

## 5. 모바일 경험

### 화면 구조

하단 내비게이션은 **현장 홈 / LOT 찾기 / 내 업무 / 더보기**의 4개다. 음성은 메뉴가 아니라 홈과 업무 상세에 있는 일관된 주 행동이다. 문서·규칙·설정은 더보기로 접근한다.

```text
┌──────────────────────────────┐
│ 임진강김치     생산 담당       │
│ 샘플 기록 · 2026.09.03 기준   │
│                              │
│ 지금 확인할 업무              │
│ [검토 필요] 발효 기록 확인    │
│ 제품 · 전체 LOT ID            │
│ 확인 사유       [업무 열기]    │
│                              │
│ 선택 LOT: 미선택 [LOT 찾기]   │
│         [마이크 · 말하기]     │
│         [직접 입력하기]       │
│                              │
│ 이어 할 업무                 │
│ 저장된 메모 · 마지막 확인점   │
│ 홈 | LOT 찾기 | 내 업무 | 더보기│
└──────────────────────────────┘
```

- 한 화면에는 주 행동 하나를 강조한다. 홈은 말하기, 음성 검토는 전송, 결과 화면은 다음 확인이다.
- 주요 터치 영역은 제품 목표로 48×48 CSS px 이상, 말하기 버튼은 64px 이상으로 잡는다. 장갑 사용성은 실기기로 별도 검증한다.
- 본문·입력은 기본 16px, 보조 문구도 읽을 수 있는 대비를 유지한다. 색과 함께 상태 텍스트를 표시한다.
- 360~430px 실기기 중심으로 확인하고 320px·200% 확대에서도 주요 기능이 잘리지 않게 한다.
- 키보드가 열려도 입력·전송·취소가 보이도록 하고 safe-area와 동적 화면 높이를 반영한다.
- 모바일 표는 핵심 필드 카드 + 원본 보기로 제공한다. 전체 원본 표가 필요할 때만 내부 가로 스크롤을 사용한다.
- LOT 검색은 전체 번호·제품·공정으로 시작한다. QR/바코드 스캔은 라벨 규격 확인 후 후속 추가한다.

### 음성 대화의 기본 계약

**탭 시작 → 말하기 → 탭 종료 → 변환 문장·대상 확인 → 전송 → 짧은 답변 → 다음 행동**

길게 누르기와 자동 전송을 기본으로 삼지 않는다. 녹음 종료와 질문 전송은 별도 행동이다. 첫 사용 안내에는 ‘종료한 녹음은 음성 변환 서비스로 전송되며, 변환한 문장을 확인한 뒤 질문을 보냅니다’를 설명한다. 녹음 취소 시 업로드하지 않는다.

| 상태 | 표시와 가능한 조작 | 처리 원칙 |
|---|---|---|
| 준비 | 말하기 / 문자 입력 | 사용자가 누르기 전 마이크 권한을 요청하지 않음 |
| 권한 요청 | 권한 안내 / 취소 | 거부되면 문자 입력과 파일 선택 제시 |
| 녹음 중 | 경과시간 / 종료 / 취소 | 녹음 표시 유지, 기본 상한 60초 제안 |
| 변환 중 | 문장으로 바꾸는 중 / 취소 | 중복 업로드 차단, 실제 진행률을 모르면 퍼센트 금지 |
| 확인·수정 | 편집 가능한 문장 / LOT·수치 / 전송 | 빈 문장 전송 금지, 애매한 LOT는 후보 확인 |
| 답변 대기 | 기록 확인 중 / 대기 취소 | 재전송 방지, 취소 후 늦은 결과는 현재 화면에 반영하지 않음 |
| 답변 준비 | 요약 / 근거 / 다음 확인 / 듣기 | 글로 먼저 제공, 자동 재생 기본 끔 |
| 재생 중 | 정지 / 다시 듣기 | 새 녹음 시작 전 재생 중지 |
| 실패 | 원인에 맞는 안내 / 재시도 / 문자 전환 | 작성 문장 유지, 오류로 전체 대화를 지우지 않음 |

녹음 상한 60초는 초기 UX 정책 제안이며 현장 테스트 후 조정한다. 최대 파일 크기는 현재 서버 제한인 20MiB 이내에서 일치시킨다. 앱이 배경으로 가거나 화면이 잠기면 녹음을 중지하고 업로드 전 확인 상태로 돌아오게 하며, 계속 녹음된다고 보장하지 않는다.

### 음성 인식 오류를 다루는 방법

- ‘이거’, ‘이 LOT’는 화면에 선택된 대상을 뜻한다. 선택 대상이 없으면 한 번에 하나의 질문으로 확인한다.
- LOT 번호는 자유 발화만으로 자동 확정하지 않는다. DB에 존재하는 후보와 제품·공정을 함께 보여준다.
- 수량·날짜·온도·단위는 변환 문장에 강조하고 사용자가 수정할 수 있게 한다. 유사 번호를 조용히 치환하지 않는다.
- STT가 신뢰도 값을 제공하지 않으면 ‘인식 정확도 98%’ 같은 수치를 만들지 않는다. 존재 여부·후보 충돌 여부로 확인을 유도한다.
- 음성 답변은 결론·누락·다음 행동을 2~3문장으로, 보통 10~20초를 목표로 설계한다. 긴 표와 전체 문서명은 화면으로 안내한다.
- ‘AI 생성 음성’임을 표시한다. 실제 수치와 단위는 화면의 근거 값에서 가져오고 읽기 편한 발음만 별도로 처리한다.

### 현장 실패·복구 경험

| 상황 | 사용자에게 보여줄 것 | 복구 |
|---|---|---|
| 주변 소음·인식 불가 | “문장을 확인하지 못했어요” | 재녹음 / 문자 입력 / 자주 쓰는 질문 |
| 통신 끊김 | “연결되지 않았어요. 아직 전송되지 않았습니다” | 현재 문장 유지, 연결 후 명시적 재전송 |
| AI 사용 설정 없음 | “음성 기능을 사용할 수 없습니다” | 가능한 데모 조회와 문자 입력 제공 |
| 권한 거부·미지원 | 짧은 원인과 설정 안내 | 문자 입력, 녹음 파일 선택 |
| 권한 요청 대기 중 취소 | 준비 화면으로 복귀 | 늦게 허용된 스트림도 즉시 종료 |
| 배경 전환·전화 수신 | 녹음 중단 안내 | 남은 녹음을 확인하거나 다시 녹음 |
| 재생 차단·오디오 장치 문제 | 텍스트 답변 유지 | 듣기 다시 누르기, 정지 가능 |
| 오래된 데이터·누락 | 실제 기준시각 / 미확인 | 갱신 또는 추가 확인 요청 |

초기 버전은 오프라인 AI를 제공하지 않는다. 연결이 끊긴 동안 보이는 기록은 마지막 조회 시각을 명시한다. 공용 단말에 음성·업무를 장기 저장하지 않으며, 오프라인 영속 저장은 별도 검토한다.

## 6. PC 웹 경험

### 정보 구조

주 메뉴: **업무 홈 / 검토 업무 / LOT 추적 / 지식·기준 / 관리**.

- 업무 홈: 우선 확인, 내가 이어 할 일, 받은 인계, 데이터 갱신 상태.
- 검토 업무: 품질, 출하, 거래처 문의·클레임을 업무 유형으로 필터링.
- LOT 추적: 현행 검색·공정 계보·실측 기록을 유지하고 업무에 연결.
- 지식·기준: 문서·검토 규칙 통합 진입. 문서와 규칙 자체는 별도 탭과 출처로 구분.
- 관리: 데이터 허브, 사용자·권한, 연결 상태. 일반 사용자의 기본 여정에서는 노출을 줄인다.

### 작업 화면

```text
┌──────────┬───────────────────────────┬─────────────────────┐
│ 업무 홈   │ 품질 검토 / 선택 업무      │ 업무 에이전트       │
│ 검토 업무 │ LOT · 상태 · 담당 · 기준일 │ 선택 LOT · 업무 문맥│
│ LOT 추적  ├───────────────────────────┤                     │
│ 지식·기준 │ 결론 / 확인된 사실 / 누락  │ 요약 답변           │
│ 관리      │                           │ 근거 열기           │
│           │ 계보 | 측정 | CCP | 문서  │ 다음 확인           │
│           │                           │                     │
│           │ 검토 메모 · 인계 이력      │ 질문 / 말하기       │
│           │ [저장] [인계] [검토 완료]  │                     │
└──────────┴───────────────────────────┴─────────────────────┘
```

1440px 기준 왼쪽 탐색 약 216px, 오른쪽 에이전트 약 340~380px, 나머지는 작업 영역으로 계획한다. 1024px 전후에서는 에이전트를 열고 닫는 패널로 전환하며 업무 내용의 가독성을 먼저 확보한다.

- 에이전트는 선택 업무·LOT·조회 기간을 알고 시작한다. 문맥 칩을 사용자가 바꾸거나 제거할 수 있다.
- 업무를 바꾸면 ‘새 업무 대화’로 전환하고 이전 업무의 대화를 보존한다. 이전 LOT가 새 질문에 조용히 적용되지 않게 한다.
- 근거를 클릭하면 해당 레코드·문서·시각으로 이동한다. 모든 조회 기록을 탐색할 수 있어야 한다.
- 초안 수정, 인계, 검토 완료는 작업 영역에서 한다. 대화 답변 속 문장만으로 완료 상태를 바꾸지 않는다.
- 메뉴 이동·새로고침·직접 링크에서도 업무가 복원된다. 접근권한이 없으면 업무 내용을 표시하지 않는다.

### 답변을 업무로 연결하는 형식

1. **핵심 결론:** 질문에 대한 짧은 답.
2. **확인된 사실:** 조회된 값과 기준시각.
3. **미확인 사항:** 없는 기록·충돌·검토되지 않은 항목.
4. **다음 확인:** 현재 데이터와 권한으로 실행 가능한 버튼 1~3개.
5. **근거:** DB 레코드·문서·규칙을 각각 열기.

버튼 예: ‘LOT 계보 열기’, ‘CCP 기록 보기’, ‘측정 이력 비교’, ‘검토 메모 작성’, ‘인계 초안 작성’. 저장되지 않은 결과는 ‘초안’으로 표시한다. ‘출하 가능’은 확인된 승인 상태를 설명할 때만 쓰며, 근거 누락을 승인으로 추론하지 않는다.

## 7. 기기 간 연속성과 업무 상태

업무 건은 대화 세션과 별도로 저장한다. 서버의 사용자·조직 인증이 기기 간 동일 사용자를 확인하고, 업무 ID가 모바일과 PC를 연결한다.

| 상태 | 의미 | 전환 주체 |
|---|---|---|
| 새 업무 | 아직 검토 시작 전 | 사용자 생성 또는 출처가 있는 규칙 기반 제안 |
| 확인 중 | 근거·현장 확인 진행 | 담당자 |
| 인계 대기 | 담당자 지정과 요청 저장, 수신 미확인 | 인계자 |
| 검토 대기 | 수신 확인 후 후속 검토 필요 | 수신자 |
| 검토 완료 | 검토 결과와 미해결 여부 기록 | 권한 있는 담당자 |
| 재확인 | 새 근거·반려로 다시 확인 필요 | 담당자 또는 갱신 알림을 받은 사용자 |

업무의 검토 상태와 ERP의 출하 승인·CCP 처분 상태는 별개 필드다. 검토 완료로 생산 시스템의 상태를 바꾸지 않는다. 읽음, 수신 확인, 검토 완료도 각각 구분한다.

인계 최소 항목: 대상 LOT, 확인된 사실, 미확인 사항, 요청사항, 수신자, 기한(선택), 근거 ID와 시각. 저장 성공 시각과 상태를 보여주고, 실패하면 초안을 유지한다.

동시에 편집했으면 버전 충돌을 알려 최신본과 내 초안을 비교한다. 과거 답변의 근거는 스냅샷을 보존하고 새 자료가 들어오면 ‘답변 후 갱신됨’을 표시한다. 마지막 기기의 메모리·공통 접근 코드만으로 이어보기를 구현하지 않는다.

## 8. 출시 범위

| 단계 | 포함 | 사용자 가치 | 다음 단계 전제 |
|---|---|---|---|
| 2.0-A 현장 경험 시제품 | 모바일 홈, 직접 녹음, 문장 확인, 정지 가능한 음성 출력, 문맥 유지, PC 업무 진입 재구성, 누락 표시 | 현장 질문과 근거 검토를 짧게 연결 | 실제 휴대전화·실제 음성 API 검증 |
| 2.0-B 연결된 업무 파일럿 | 조직 로그인, 저장 업무, 인계함, 근거 스냅샷, 기기 간 이어보기, 출하·클레임 초안 | 현장 확인에서 담당자 검토까지 연결 | 권한·동시 편집·감사 이력 검증 |
| 2.1 현장 연동 확장 | ERP·IoT 연동, 다중 부모 LOT, 라벨 스캔, 필요한 알림 | 실제 운영 자료와 여정 연결 | 현장 데이터 계약과 운영 책임자 확정 |

**v2.0 고객 여정의 완료 기준은 2.0-B까지다.** A만 완성하면 음성 UX 시제품으로 표기한다. 항상 듣기, 웨이크워드, 백그라운드 연속 대화, 자동 공정 제어, 자동 출하 승인, 고객 자동 발송은 초기 범위에 넣지 않는다.

## 9. 성공 지표와 검증

아래 수치는 성능 실적이 아닌 초기 제품 목표다. 현행 흐름의 기준값을 먼저 측정한 뒤 파일럿에서 조정한다.

| 지표 | 정의 / 초기 목표 |
|---|---|
| 첫 업무 진입 | 홈 표시부터 적절한 업무 열기까지 중앙값 15초 이내 |
| 음성 질문 완료 | 녹음 시작 세션 중 문장 확인 후 전송에 성공한 비율 90% 이상, 사용자의 의도적 취소는 별도 집계 |
| 대상 식별 | 검증 시나리오에서 미확정 LOT를 임의 확정한 사례 0건 |
| 음성 변환 지연 | 10초 발화 종료부터 편집 가능한 문장 표시까지 P95 8초 이내 목표; 네트워크·기기별 분리 |
| 답변 지연 | 전송부터 핵심 답변 표시까지 P95 15초 이내 목표; AI와 데모 분리 |
| 여정 완료율 | 현장 확인 → 저장 → PC 검토 시나리오를 도움 없이 마친 비율 85% 이상 |
| 처리시간 | 동일 검토 시나리오의 중앙 처리시간을 기존 흐름 대비 30% 줄이는 목표 |
| 데이터 정직성 | 누락·과거·샘플 데이터의 필수 표시 누락 0건 |
| 오류 복구 | 네트워크·권한·변환 실패 후 작성 문장 소실 0건 |

초기 사용성 테스트는 역할별 2~3명, 총 6~9명을 제안한다. 방향성을 찾는 탐색 테스트이며 통계적 성능 보증으로 표현하지 않는다. 조용한 사무실과 실제 허용된 작업 장소에서 같은 과제를 수행한다.

필수 과제: ① 교대 브리핑 ② LOT 음성 오인식 수정 ③ CCP 근거 확인 ④ 모바일 저장 후 PC 이어보기 ⑤ 출하 검토 ⑥ 클레임 회신 초안 ⑦ 권한·통신 실패 복구. 실제 iPhone Safari와 Android Chrome을 포함하고, 파일럿 시작 시 OS·브라우저 버전을 기록한다.

분석 이벤트는 `task_opened`, `voice_started`, `voice_cancelled`, `transcript_ready`, `transcript_edited`, `question_submitted`, `answer_ready`, `evidence_opened`, `task_saved`, `handoff_sent`, `handoff_acknowledged`, `task_resumed`, `review_completed`로 계획한다. 분석용 로그에 원음·전체 문장·API 키를 넣지 않는다.

## 10. 우선순위와 일정 가정

기간은 기존 코드 기반으로 프론트엔드 1명·백엔드 1명·기획/현장 검증 지원이 있다는 조건의 추정이다. 자격증명·로그인·현장 참여자 확보에 따라 달라지며 확정 일정이 아니다.

| 순서 | 예상 기간 | 산출물 |
|---|---|---|
| 현장 여정 확인 | 3~5 업무일 | 역할·환경·상위 5개 업무, 현재 소요시간 |
| 2.0-A 구현·사용성 점검 | 1~2주 | 모바일 직접 음성, 문맥 유지, PC 검토 흐름 |
| 2.0-B 구현·통합 검증 | 2~3주 | 로그인·저장·인계·기기 간 복원 |
| 제한된 파일럿 | 1주 | 실기기·소음·데이터 검증, 수정 목록 |

첫 개발 단위는 **모바일 LOT 질문 → 확인된 문장 전송 → 근거 보기**로 잡는다. 다음 단위는 같은 결과를 저장해 PC에서 이어 검토하는 흐름이다. 세부 티켓·데이터·수용 기준은 [개발 명세](v2.0-delivery-spec.md)에 정리한다.

## 11. 구현 시 확인할 기술 근거

- 마이크 접근은 보안 컨텍스트와 사용자 권한을 전제로 설계한다. 운영 주소는 HTTPS를 사용한다. [MDN getUserMedia](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia)
- 녹음 MIME 형식은 브라우저 이름으로 고정하지 않고 실행 시 지원 여부를 확인한다. [MDN MediaRecorder.isTypeSupported](https://developer.mozilla.org/en-US/docs/Web/API/MediaRecorder/isTypeSupported_static)
- WCAG 2.2 AA의 최소 타깃 기준은 예외 조건을 포함한 24×24 CSS px다. 본 기획의 48px는 현장 조작성을 위한 더 큰 제품 목표다. [W3C 타깃 크기 설명](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum)

음성 공급자 모델명과 비용은 이번 기획에서 새로 선택하지 않았다. 현재 서버 경로를 우선 재사용하고, 실제 인식·지연·비용을 측정한 뒤 스트리밍 필요 여부를 판단한다.
