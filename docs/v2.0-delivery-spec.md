# Agent v2.0 개발 명세와 수용 기준

작성일: 2026-09-23 · 상태: 제안 명세 / 미구현

제품 의도와 전체 여정은 [v2.0 재기획](v2.0-product-plan.md)을 따른다. 이 문서의 신규 파일·API·데이터 필드는 앞으로 구현할 계약이며, 현재 존재하는 것으로 간주하지 않는다.

## 3. 음성 구현 계약

1. 진입 시 기능 탐지만 한다. `isSecureContext`, `navigator.mediaDevices?.getUserMedia`, `MediaRecorder` 지원과 서버 기능 메타를 확인한다.
2. 사용자의 시작 클릭에서 마이크 권한을 요청한다. 허용된 스트림은 하나만 소유한다.
3. 지원 MIME 후보를 런타임에서 검사한다. 실제 선택한 MIME에 맞는 확장자와 `Content-Type`을 보낸다. 후보가 없으면 브라우저 기본 형식을 확인하거나 파일/문자 경로로 전환한다.
4. `stop` 후 마지막 `dataavailable`까지 모은 Blob을 전송한다. 빈 파일·크기 상한을 클라이언트와 서버 양쪽에서 확인한다.
5. 녹음 취소는 Blob을 버리고 업로드하지 않는다. 변환 중 취소는 클라이언트 대기를 중단하되 이미 시작된 공급자 처리·비용까지 중단된다고 안내하지 않는다.
6. 종료·취소·권한 오류·초기화·컴포넌트 해제·배경 전환 시 미디어 트랙과 타이머를 정리한다. TTS 교체 시 오디오 객체와 URL을 정리한다.
7. STT·TTS·질문에 작업 세대 번호와 요청 ID를 붙인다. 늦게 끝난 이전 요청이 새 입력·답변·음성을 덮어쓰지 못하게 한다.
8. 전송 잠금은 React 렌더 전에 중복 클릭을 막을 수 있는 즉시 잠금과 서버 중복 방지로 처리한다. 질문·추천·음성 경로를 같은 제출 함수로 통합한다.
9. 초기화하면 녹음·재생·대기 중 요청을 정리하고 서버 대화 연결도 초기화한다. 실패한 초기화를 성공처럼 표시하지 않는다.
10. 원음은 애플리케이션에서 장기 저장하지 않는 기본 정책을 제안한다. 외부 공급자의 데이터 처리 조건은 운영 설정 시 별도로 확인하며 저장하지 않는다고 임의 보장하지 않는다.

초기 음성 파이프라인은 현재 STT → `/api/chat` → TTS를 재사용한다. 전이 규칙을 먼저 완성한 뒤 지연 측정에 따라 스트리밍을 검토한다. 공급자 비밀키는 계속 서버에서 관리한다.

## 4. 제안 데이터 모델

| 엔터티 | 주요 필드 | 규칙 |
|---|---|---|
| WorkItem | id, organization_id, type, lot_id, title, status, assignee_id, due_at, version, created_at, updated_at | 제조 원본과 별도, 조직·담당자 검증 |
| WorkNote | id, work_item_id, author_id, text, created_at | 수정 이력을 남기거나 새 버전 작성 |
| Conversation | id, work_item_id?, user_id, context, updated_at | 공급자 response ID는 서버 내부 |
| Message | id, conversation_id, role, text, summary, context_snapshot, created_at | 저장 범위·보존 기간을 운영 정책으로 설정 |
| EvidenceSnapshot | id, message_id, source_type, source_id, source_version, record_time, retrieved_at, content, content_hash | 답변 당시 근거 보존, 문서 개정·승인상태 포함 |
| Handoff | id, work_item_id, sender_id, recipient_id, request, status, sent_at, acknowledged_at | 명시적 인계, 수신 확인 별도 |
| AuditEvent | id, organization_id, actor_id, entity_id, action, previous_version, next_version, at | 인계·상태 변경 추적, 비밀키·원음 금지 |

운영 저장소는 현재 PostgreSQL 기반을 확장한다. SQLite는 로컬 데모로 유지한다. 사용자와 조직은 선택한 인증 공급자의 검증된 식별자에 연결한다. 업무 대화·감사·근거의 보존기간과 삭제 권한은 파일럿 전에 운영 책임자가 정한다.

## 5. API 변경 제안

| API | 현재/신규 | 계약 |
|---|---|---|
| `GET /api/workspace` | 확장 | 데이터 기준시각, 조회시각, 기능별 가능 상태; 전체 회사 데이터는 역할에 맞게 제한 |
| `GET /api/lots/{id}` | 유지·보강 | 미확인과 빈 결과를 구분; 후속 조직 권한 검사 |
| `POST /api/chat` | 확장 | 기존 question/lot_id/mode 유지, context·request_id 추가; 문맥·LOT 유효성 검사 |
| `POST /api/chat/reset` | 보강 | 대상 대화의 연결 초기화, 진행 중 요청이 연결을 되살리지 않도록 버전 검사 |
| `POST /api/voice/transcribe` | 보강 | 기존 multipart 유지, 크기·유형·동시성·시간 제한, 취소와 오류 구분 |
| `POST /api/voice/speak` | 보강 | 요약 텍스트, 길이 제한, 동시성 제한, 명시적 오류 상태 |
| `GET /api/work-items` | 신규 | 역할별 필터, 유형·상태·담당·페이지 조회 |
| `POST /api/work-items` | 신규 | 업무·근거 스냅샷 저장, 중복 요청 키 |
| `GET /api/work-items/{id}` | 신규 | 업무·문맥·메모·근거·이력; 권한 확인 |
| `PATCH /api/work-items/{id}` | 신규 | expected_version과 허용 필드만 갱신, 충돌 시 409 |
| `POST /api/work-items/{id}/notes` | 신규 | 메모 저장, 작성자 서버 결정 |
| `POST /api/work-items/{id}/handoffs` | 신규 | 같은 조직의 허용된 수신자, 요청·근거·중복 키 |
| `POST /api/handoffs/{id}/acknowledge` | 신규 | 수신자 본인 확인, 멱등 수신 확인 |

권한 없는 업무 ID를 URL에 넣어도 접근할 수 없어야 한다. CSRF 방어와 HTTPS 세션 쿠키, 사용자·조직 단위 호출 제한을 적용한다. 숨겨진 메뉴만으로 권한을 통제하지 않는다. 조회 전용 경로 역시 운영 데이터 연결 전 인증 범위를 점검한다.

새로고침 가능한 업무 URL을 도입할 때 현재 `/`만 제공하는 정적 서버를 보강한다. 앱 경로에만 SPA fallback을 적용하고 존재하지 않는 `/api/*`와 자산 요청은 올바르게 404로 남긴다.

### 답변 확장 계약

기존 `text`, `evidence`, `records`, `mode`는 호환을 유지한다. 신규 필드는 다음 의미를 가진다.

- `summary`: 듣기·모바일 요약에 사용할 짧은 답변. 원문과 모순되지 않게 근거와 연결.
- `context`: 확정된 LOT·업무·질문 기준기간. 요청한 문맥과 실제 사용 문맥이 다르면 표시.
- `facts`: 값·단위·기록시각·evidence_id가 연결된 확인 사실.
- `unknowns`: 누락·오래된 기록·충돌 등 미확인 사항.
- `actions`: 허용된 행동 유형과 대상 ID. 브라우저가 임의 코드·URL을 실행하는 지시가 아님.
- `record_evidence`: source_type, record_id, lot_id, recorded_at, retrieved_at, snapshot_id.

문서 근거와 실측 근거의 개수를 구분한다. 전체 응답을 소리 내어 읽는 대신 summary를 기본으로 사용한다. 요약을 만들지 못해도 텍스트 답변은 사용할 수 있다.

| B04 | 인계 연타·수신자 변경·수신 확인 | 중복 인계 없음; 수신자 검증; 수신과 완료 상태 분리 |

| B06 | 새 원본·문서로 재조회 | 과거 답변 스냅샷 유지, 새 근거 표시 |
| B07 | 업무 직접 링크 새로고침 | 앱 복원 성공, 잘못된 API는 404 |
| B08 | 클레임 회신 초안 | 근거·미확인 표시, 내부 민감정보 제외, 외부 발송 없음 |

자동화는 상태 전이·중복·취소·권한·충돌·근거의 핵심 불변조건에 집중한다. 실제 마이크 권한·소음·코덱·전화 수신·백그라운드·재생은 실기기 체크리스트로 별도 검증한다. 시뮬레이션된 음성 성공만으로 음성 기능 검증 완료라고 하지 않는다.

## 7. 파일럿 전 확정할 항목

- 상위 업무 5개와 첫 파일럿 사용자: 생산·품질·출하 중 누가 먼저 쓰는가.
- 현장 기기·브라우저·소음·위생구역 정책·이어폰 허용 여부.
- 기존 로그인·사용자 명부·조직·역할과 내부 인계 책임.
- 원본 데이터 제공 주기, 승인 기록의 기준 시스템, 문서 개정·승인 책임자.
- 대화·메모·근거 보존기간과 공용 단말 로그아웃 정책.

이 항목들은 파일럿 운영 조건이다. 2.0-A의 조회·음성 UX 개발은 기존 샘플과 명시된 가정으로 진행할 수 있다.
